## Deliberate migration procedure

1. Review compatible destination runtime code and custody/proxy authorities, economically equivalent tokens at identical decimals/nominal units, and actual provider funding/finality/retry behavior. A governance approval is not proof of perpetual destination custody.
2. Onboard any missing immutable provider/channel policies and append-only principal, source-completion ACK, canonical-location ACK, and reward routes through each deployment's governance controller. For a satellite B-to-C hop, register its remote-only policy and principal graph edge on the canonical chain too. Confirm wrapper/runtime/configuration pins, policy-to-route bindings, explicit source outbound enablement, and canonical token mappings across all participants before moving funds; module bindings and router endpoints are not replaced.
3. Schedule/execute the source governance proposal. Review the economic NFT, source pool, next custody epoch, immutable home identity, canonical asset mappings, and earliest execution time. Each approved move is immediately eligible; the keeper does not select a new chain autonomously.
4. A keeper calls `ZZZMigration.execute` immediately after plan approval when all execution guards pass, paying the bridge's native fee from operator funds. Watch source finality and provider status. No timeout permits a principal refund.
5. Verify destination `PrincipalAccepted`/`ImportPending`, the retained accepted-message snapshot, epoch, and exact token backing. A revisited satellite must have a drained old `Remote` record and accept a strictly newer local epoch. A keeper calls receiver `finalize` with fresh bounds; failed LP activation is retried without redirecting principal.
6. Call destination `acknowledge(migrationId, reverseRouteId)` for source completion. Confirm that the immediately previous source becomes `Remote` and its plan completes. When that source is the canonical home, this ACK also records the new home location.
7. For an onward hop between satellites, also call `acknowledgeHome(migrationId, homeRouteId)`. Verify canonical location events in strict next-epoch order. An out-of-order notification must be retried after earlier location updates; historical exact retries cannot regress the location. ACKs use the retained hop snapshot even if custody has since moved again.
8. On canonical return, location is recorded atomically during principal import; do not construct a self-chain home ACK. Send source completion to the satellite that released custody. No imported hop remints the NFT, creates another collective member or changes royalty weight.
9. Drain funded old remote reward budgets through their historical authorized routes, even after principal has left a source. The keeper attempts reviewed reward routes in Active, Outbound, Remote and Inbound states; it performs LP operations only in Active. Immutable NFT/token provenance selects the canonical asset; satellite dust joins the funded individual budget. Keep reward and principal reconciliation separate.

Source failure before successful submission reverts that transaction. Failure after a provider has taken custody requires its provider-specific recovery process, which is **not implemented by the generic router or adapter**. There is no safe catch-all admin recovery address. Real SDK wrappers and live bridging remain deferred until separately implemented, reviewed and staged.

This procedure covers equivalent-asset custody hops, not arbitrary conversion, NFT chain changes or satellite holder top-ups. The selected native/Pons candidate keeps migration assets as nonzero WETH/ZZZ through accounting normalization; only the physical venue key contains native address zero. Actual provider/route qualification remains deferred, and creator-payment intake remains separate.
