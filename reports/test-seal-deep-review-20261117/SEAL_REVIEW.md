# Irreversible configuration and after-seal review

This review covers all **61 current Solidity source files**: 40 concrete component sources, five abstract bases, eight libraries and eight interface files. Each component below has a curated source assessment; the companion JSON adds exact source hashes, constructor bodies, immutable declarations and lexical locations of seal/one-time/limit candidates. Lexical matches are navigation evidence, not proof that every function or dependency is safe. The review does not turn a successful generic seal into production approval.

The baseline is `003c8d8dc88b60cbfbcc8caf61fa864c6487b40f`. The two newly approved source guards reject a Vault home-chain identity different from the current chain and bare `ipfs://` / `ar://` roots. Empty NFT constructor staging remains; sealing still requires a populated root. Portable EVM controls deploy hash-pinned historical creation bytes to demonstrate the old bad acceptance, then check current rejection. The separate reservation correction restricts new bucket IDs while retaining existing aliases; its final source/test evidence is tracked separately.

## Binding order and release boundary

1. Deploy controller-owned factories and bind the actual ProtocolPolicy before constructing the Vault. Constructor-owned children inherit their creating parent and cannot later be rebound.
2. Bind the current NFT/Vault/Fees peers before constructing their typed canonical companions; validate every component's controller, version and real runtime. Controller bind is append-only even before seal: a wrong already-bound peer often requires a new graph.
3. Configure independently qualified dual prices before fixed ZZZ source identity; add that exact ZZZ to Rewards; configure Migration's matching identity only after source/Rewards/Buyback agreement. No token replacement, bridge or external principal-custody recipient is available.
4. Validate actual pinned native venue graph and admission, derive exact reservation identity with Migration.validation already bound, then configure future pool/range/evidence policies. A pool ID alone does not enable another core/version/chain or an arbitrary token.
5. For the selected release, bind actual SeaDrop helper and selected converter before seal; verify the complete sale stages/payers/fees/proceeds, mint deadline, artwork catalogue and VRF, as well as live price/routes and gas. These are separate from generic Access.seal's narrower code checks.
6. Review the entire readiness output and unresolved fields before sealing. A nonzero review hash attests an operator decision; it does not prove missing external facts. Static plans do not sign/deploy/seal or approve a provider.

Canonical replacement is conditional recovery, not universal in-place upgradeability: it needs a fresh prepared importer before seal, compatible fixed schema/SeaDrop transport, completed old draws, exact royalty cohort state, parked principal, transferable full backing and funded activation/abort. Terminal holder return is irreversible and does not reopen LP or provide an integrated token/chain bridge.

## Guard verification
+
+Six distinct selected methods pass; no unchanged suite is rerun. Three initial methods cover the current zero/local chain choices, actual NFT constructor rejection and recoverable empty bootstrap setup without consuming its one-time root write. Those retain their original two-fix source stage before the unrelated reservation change. Two final portable controls actually deploy the authenticated old bytecode, demonstrate its bad acceptance and verify current exact rejection. One adapted CanonicalHandoff method rejects a foreign-home Vault constructor while preserving the operating source and inert importing destination.
+
+The canonical pass has current production sources but an explicitly recorded prior `test/VaultAccounting.t.sol` compiler input: its `VaultPolicyMock`, used by `PreparationPolicy`, is unchanged; later added unused execution fixtures are not relabelled as tested. Exact per-source/artifact hashes and stage limits are in [SEAL_GUARD_VERIFICATION.json](SEAL_GUARD_VERIFICATION.json). Initial permission/harness failures, the discarded compiler-stack failure and the overlapping superseded chunked control run remain separate in [SEAL_TEST_ATTEMPTS.json](SEAL_TEST_ATTEMPTS.json); they do not add feature coverage or establish contract failures.
+
+The final portable controls read only public tracked historical fixtures. [SEAL_TEST_CONFIG_DELTA.json](SEAL_TEST_CONFIG_DELTA.json) proves the sole Foundry change is read permission for that fixture directory: compiler settings, size/gas limits and FFI are unchanged. Historical fixture bytes are never production configuration. The separate reservation tests and normal/static build evidence are owned by the parent report, not double-counted here.
+
+## Evidence limits
+
No network/provider/asset/content/SeaDrop/VRF acceptance is inferred. No public or existing local transaction, service, signer, journal, website or heartbeat was changed by this inventory. Source assessment and the narrowly selected constructor/root/reservation regressions are different evidence classes. Historical bytecode controls are test-only, explicitly pinned and excluded from normal production compilation. Exact per-test source artifacts and outcomes belong to the verification record; an unchanged suite is not rerun to inflate coverage.
