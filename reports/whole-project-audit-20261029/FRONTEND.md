## Implemented repair: ownership hidden by optional currency outage

**F-01 — confirmed availability defect, repaired.** `Projection.wallet()` previously required every admitted asset runtime/decimals read to succeed before returning a complete ownership inventory. Current website `DeploymentAPI.portfolio()` requests that inventory before loading cards. A malformed/reverting optional royalty-token metadata read therefore hid all otherwise healthy holdings, defeating the isolated-currency design already used by wallet summaries, collection views and opt-in NFT royalty reporting.

The endpoint now calls the existing `_admitted(..., asset_health={})` path. The admitted address inventory, configured allowlist, required contract runtime/binding/lifecycle checks, complete indexed history, on-chain balance/owners and final canonical confirmation remain strict. This endpoint returns no financial balance, quote, asset-health guarantee or valuation. It does not turn a failed currency into zero, enable a claim, or relax the selected-asset checks in unsigned preparation. No Solidity, economic right, schema or signing behavior changed.

Fresh negative evidence reaches the actual malformed static ABI result in both accounting3 and accounting4 after a healthy inventory control succeeds. Seven new distinct methods pass after the repair: both current profiles, metadata/runtime faults, token RPC fault versus unskippable work budget, changed admitted addresses, required core runtime fault, ownership/depth fault, and verified empty inventory. The tests use the existing real SQLite/indexer history fixture plus byte-level RPC responses; they do not use a public network. An initial subtest cleanup issue was corrected and its unsuccessful transcript retained. `docs/FRONTEND_API.md` explains the new boundary.

## Snapshot, delay and concurrency conclusions

`Projection._snapshot/_finish` verifies chain, deployment anchor, required depth, exact requested header and freshness after the last network read. All monetary contract reads remain EIP1898 `requireCanonical`. This does not protect against a coherent dishonest provider or qualify actual archive/trace support.

The website has two intentional snapshot domains: a complete inventory anchor for wallet totals/earnings and collection aggregation, versus each card's independently confirmed NFT plus matching earnings hash. It labels card block numbers and the portfolio footnote says each card is its own snapshot. No code path sums the eight visible cards as the full wallet. An owner transfer between anchor/card reads rejects the older inventory's card instead of fabricating ownership or dropping accrued rights. Re-read/unavailable behavior can inconvenience a user during movement but is safer than mixing rights; no patch justified from this source review alone.

Session/provider/account/page changes increment revisions, cancel owned fetch controllers, clear a review and suppress stale asynchronous results. Wallet and RPC timeout does not mean the extension prompt canceled or a send failed. A saved hashless intent or pending hash blocks a fresh local submission. Exact canonical receipt identity and fee caps are verified independently of the wallet; confirmation is retained until API/Entry reconciliation succeeds, then canonical inclusion is rechecked before journal acknowledgement. No receipt mismatch is solved by deleting a journal or sending again.

For an approval, the next complete Entry transaction is independently prepared using new allowance/prices; insufficient allowance after confirmation cannot silently request a second approval. ETH needs no ERC20 approval. An existing exact allowance can make ZZZ activation one transaction. Successful LP means actual canonical pool execution, not the approval. A reverted atomic contribution applies no LP change; gas can still be spent. New fee income after a claim is valid.

## Capacity and latency: enforced bounds versus unknown performance

Current source defaults:8 HTTP connections,4 process supervisors;2 active per client, reads1/sec with burst12 and preparations6/min with burst2. Workers spawn separately, hard30sec/1MiB result; request work defaults25sec/1024 RPC calls/2048 posts. Ingress5sec, headers32KiB/line8KiB, connection45sec. Card requests use8/page and2 in flight; whole-inventory aggregates use ordered16-item chunks and can be unavailable if the anchor expires. These are safeguards, not throughput or latency promises.

The browser read transport defaults15sec per request; API requests30sec/2MiB; local wallet polling is at most21 attempts within45sec by default, submission uncertainty at90sec. A wallet request raced against a timer may remain open in the extension. Cancellation stops local result consumption; an already dispatched child may finish its bounded work before its lease returns. Coalescing/greater parallelism must not bypass client budgets or mix snapshot domains.

No measured100-user capacity, target-chain latency/gas, real provider availability, extension acceptance, immutable marketplace content retrieval or current installed-service health was established here. Those stay in the existing hosted-services/wallet/portfolio/metadata qualification tasks, rather than closing release work from these limits or mock tests.

## Rejected concerns and accepted limitations

- Do not demand a zero balance after claim or unconditional preview/batch equality: new income and valid owner callbacks can change later amounts.
- Do not call a configured zero dormant ledger weight a missing rarity: trait1/2/3 and economic membership differ. Only the downloadable fixed trait is stale.
- Do not interpret a null public deployment as a failed live wallet: this intentionally disables unqualified public signing/data, and cannot be replaced by examples.
- Do not erase or relabel old chain profiles to make fresh4 work. Existing saved intents/receipt codecs carry exact historical identities.
- Do not treat SVG asset path existence or source hashes as rendered quality, immutable hosting, OpenSea refresh or running-service attestation.
- Do not make optional token health block ownership. Conversely, required core/lifecycle/history/admission/canonical failure still blocks it; F-01 does not weaken those controls.
