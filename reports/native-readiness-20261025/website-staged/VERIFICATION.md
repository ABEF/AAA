## What is prepared

- Schema1 retains historical currency interpretation, old Entry calldata and legacy review DTOs. Declared native-V2 data is explicitly rejected under a legacy manifest; absent historical version fields remain historical. There is no version fallback.
- Schema2 explicitly requires accounting2, pricing2, routing2 and reviewed Entry1, together with ten reviewed contract runtimes, immutable parent/controller bindings, active price/admission policies and typed route identities. ETH is real currency zero with 18 decimals and no token runtime; it is never silently valued as WETH.
- The browser reads three-word `Oracle.priceBounds` at the same confirmed canonical block, verifies approved policy/asset identity and decimals, and checks ordered positive bounded prices and a nonzero fingerprint. A maximum contribution loss ceiling is explicit in the reviewed manifest (the example selects200bps). The actual Budget cap must fit that ceiling and match the preparation response. No default is inferred.
- The unsigned Entry call is independently reconstructed as `executeReviewed(Request,uint16)` with the tenth maximum-loss word. The minimum LP floor uses the rounded-up upper input value, then a rounded-up retained-value floor. Lower input value still determines the $100 activation/$5 growth minimum. Exact approvals, route minimums, marginal physical LP addition, NFT shares and separate network gas remain required.
- Native LP and royalty ETH claims can be prepared together, using two correctly selected router entries. The reviewed data inventory supports49 currencies in its union, with native LP/royalty row bounds33/17. A contribution price-read failure or an operator cap above the client ceiling does not block ordinary confirmed position reads.
- Candidate UI distinguishes the manifest's approved ceiling from the actual captured review limit and shows the verified minimum added LP. Historical presentation is preserved.

This remains **read and unsigned preparation** for nonlocal configurations. Browser-wallet.js, browser-client.js and the local-only transaction coordinator are byte-identical to the website checkout; public `DEPLOYMENT` remains null. The isolated fixture can exercise the already existing Anvil-only coordinator. This work does not enable public transaction submission.
